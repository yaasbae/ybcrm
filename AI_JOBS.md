# Безопасные фоновые AI-задания

## Назначение

`ai_jobs` — серверная очередь для будущих AI-действий. Браузер и MCP не имеют прямого доступа к коллекции. Основная CRM не зависит от работы очереди.

## Состояния

`awaiting_approval → queued → running → succeeded`

При временной ошибке: `running → retry_wait → running`. После исчерпания попыток: `dead_letter`. Владелец может перевести задание в `cancelled`.

## Гарантии первого этапа

- обязательный `idempotencyKey`: повторный запрос возвращает существующее задание;
- policy registry запрещает неизвестные типы заданий;
- `APPROVAL` не попадает в исполнение без подтверждения владельца;
- approval связан с точным hash аргументов, действует 24 часа и используется один раз;
- kill switch по умолчанию выключен, если серверная настройка отсутствует;
- Firestore transaction выдаёт lease только одному worker;
- timeout ограничивает зависшие действия;
- exponential backoff ограничен 15 минутами;
- после `maxAttempts` задание попадает в DLQ (`dead_letter`);
- истёкший lease зависшего worker автоматически возвращается в очередь;
- владелец может вернуть задание из DLQ в очередь; для `APPROVAL` потребуется новое подтверждение;
- payload ограничен 32 KB;
- создание, подтверждение, остановка и выполнение пишутся в общий AI audit log;
- безопасные executor: `system.health_check`, read-only разбор обращений и ручной пилот ежедневной бизнес-сводки;
- ежедневная сводка получает данные только через общий MCP AI Tool Layer, сохраняется в `ai_daily_reports` и не изменяет бизнес-данные.

## Защищённые API

Все маршруты owner-only и требуют Firebase ID token:

- `GET /api/ai-jobs`;
- `POST /api/ai-jobs`;
- `GET|POST /api/ai-jobs/runtime`;
- `POST /api/ai-jobs/:id/approve`;
- `POST /api/ai-jobs/:id/cancel`;
- `POST /api/ai-jobs/:id/retry`;
- `GET /api/ai-jobs/audit`;
- `POST /api/ai-jobs/run`.

Владелец управляет очередью на странице `/ai-jobs`: видит состояния, подтверждает или отменяет задания и управляет kill switch.

Кнопка «Проверить систему» создаёт отдельное идемпотентное задание `system.health_check`. Если исполнение включено, экран сразу запускает один цикл worker и показывает результат. Если kill switch выключен, задание безопасно остаётся в статусе «Ожидает запуска».

DLQ-уведомления отправляются в служебную Telegram-тему, если настроен серверный токен. Автоматический production scheduler должен вызывать `POST /api/ai-jobs/run` с серверным worker secret; настройка Cloud Scheduler выполняется отдельно от кода и требует контролируемого изменения production-инфраструктуры. До этого очередь можно безопасно запускать с owner-экрана.

## Telegram-приёмная обращений

Тему можно подключить командой `/ai_intake_here`, отправленной внутри нужной темы подключённой менеджерской группы, и отключить командой `/ai_intake_off`. Переменные `AI_INTAKE_TELEGRAM_CHAT_ID` и `AI_INTAKE_TELEGRAM_THREAD_ID` остаются серверным fallback.

Каждое текстовое сообщение менеджера в подключённой теме идемпотентно сохраняется в server-only коллекцию `ai_incidents`. Бот подтверждает номер обращения. На этом этапе обращение получает статус `new`: оно не запускает изменение CRM, исправление кода или deploy. Повторная доставка одного Telegram update не создаёт дубликат, потому что ID строится из chat/message ID.

Для обращения создаётся SAFE-задание `incident.triage`. Перед отправкой текста во внешний AI маскируются email и российские телефоны. Модель может только вернуть ограниченный JSON: категория, приоритет, краткое описание, гипотеза, уточняющий вопрос и безопасная рекомендация. Значения проверяются по allowlist и обрезаются по длине. Результат сохраняется в обращении и отправляется ответом в ту же Telegram-тему. AI не получает инструментов изменения CRM или кода.

Owner-only страница `/ai-incidents` показывает обращения и позволяет вручную запустить повторный разбор, отметить обращение решённым или отклонить его.
